# Integration and operations

## State transfer between voice, text and human support

All channels use the same authenticated customer ID, Redis session ID, `Turn` contract and `SupportService`. Whisper text is not a second conversation: the coordinator submits it as a voice turn in that session. HTTP and CLI can reuse the session, and the browser retains only its session ID in session storage. Tokens stay in memory. Reconnection reloads history; a terminated session cannot be reopened.

Redis owns state, the last authorized order reference, clarification context, bounded message history, handoff request and the most recent human resolution. A session lease serializes mutations across workers; repeated business turns use an ID plus message fingerprint and return the recorded response. A conflicting retry is rejected. History keeps the most recent 120 messages, with monotonic sequence numbers. Blocked input is redacted in history. This is operational demo retention, not a complete audit archive.

Handoff changes `active → waiting_for_human → human_active`. Automation does not classify or answer messages in either human state. Customer ownership and basic input restrictions still apply. Only an authenticated admin can see the handoff, claim it or reply. The first admin view contains an extractive history summary, requested help and verified order reference. Customer messages and human replies share persisted history. Connected clients observe it; voice-enabled customers hear human replies through Piper. No AI claim-validation is imposed on a trusted operator's authored message; operational authorization and staff training remain necessary.

Ending a human chat extracts a resolution from recent staff messages plus the optional final note, persists it, displays/speaks it and returns the same session to `active`. No Groq call is needed to end a handoff. The resolution is explicitly untrusted model context: it cannot grant tools, establish refund evidence or bypass guards. Customer End conversation terminates both sides and rejects subsequent messages. Disconnect alone allows reconnection and drains accepted work.

Accepted business jobs are FIFO. Barge-in invalidates obsolete audio playback, not accepted jobs. Every accepted turn has an ID and a completed/failed/cancelled outcome. Queue overflow is explicitly rejected and can be retried. STT failure never becomes an empty or invented business turn. Disconnect drains queued jobs within a bounded deadline; customer termination explicitly cancels work not yet begun. The queue is process memory: surviving a machine/process crash requires a durable job queue and is not claimed here.

## Production evaluation, SLOs and A/B rollout

Run `python scripts/evaluate_live_system.py --live` with working Groq credentials and Redis. Add `--retrieval --answers` after building the embedding index to exercise real grounded answers. The runner stores model/prompt provenance, routing accuracy and confusion matrix, input/output guard recall, false positives, provider errors, cache counters and wall-clock duration. Provider errors are reported separately; incomplete runs are not passing quality evidence. Use the development datasets for iteration and maintain a separate, reviewed, held-out set for release decisions.

Expand held-out cases with each intent, ambiguous/mixed messages, follow-ups, ownership attacks, prompt injections, eligibility versus refund initiation, legitimate refund questions, noisy/accented speech, handoffs and provider failures. Report per-intent precision/recall and macro F1, safety recall and false-positive rate, grounded citation accuracy, tool authorization violations, duplicate/lost accepted turns, interruption success, false interruptions, latency p50/p95/p99, and recovery success. Classifier cache hit rate is hits/(hits+misses); report request coalescing separately. A repeated scripted classifier result is a cache mechanics test, not model-quality evidence.

Provisional release objectives, to validate against load and actual provider quotas: zero authorization violations or lost accepted turns in the release suite; input-attack recall at least 98% with benign false positives below 3%; routing macro F1 at least 0.95; 99% completed-or-explicitly-recovered turns; healthy-call voice response p95 below 4 seconds. These are proposed targets, not observed results or guarantees. Report fallback and failed calls separately rather than hiding them from latency/success measurements.

Assign experiments by a stable hash of session ID, keeping a conversation on one version. Shadow new classifiers without dispatching their tools, then canary 1%, 5%, 25%, and 100% only after quality, latency, cost and safety checks. Never A/B test removal of ownership/input/output guards. Version prompt/model/cache namespace together. Roll back on safety regression, increased provider errors or exceeded latency budget. Store experiment version in traces; compare equivalent traffic and confidence intervals.

Ten thousand concurrent sessions is a deployment goal, not an achieved benchmark. Use horizontally scaled async API workers behind a WebSocket-capable load balancer, shared authoritative Redis, deployment-wide Groq quota/admission control, and bounded CPU speech/embedding worker pools. Distinguish idle connections from active synthesis/LLM requests when sizing. Run a distributed load test with actual arrival/turn rates and queue budgets; prefer explicit overload rejection to unbounded waiting. Redis Cluster, durable accepted-audio jobs, global admission control, regional failover and production identity/agent assignment require additional infrastructure.

## Outage detection, fallback and behavior consistency

Implemented protections include total turn/STT/synthesis deadlines, bounded playback windows, capped retries, categorized logs and local recovery recordings. STT transient transport/5xx/short-rate-limit failures retry at most once inside the total deadline. Authentication failures fail immediately. The browser can continue with text if only STT fails. Text still depends on Groq chat and is not a workaround for an LLM outage. Piper may retry before its first chunk; after audio begins it is stopped and a local recovery recording is used, avoiding duplicate replay. Validated text remains visible. Human chat and extractive resolution do not require Groq; speaking human messages still requires Piper or recovery audio.

For a running-call demo, explicitly enable the admin-only one-shot failure controls described in `voice-demo.md`. They can invalidate one STT request, inject one transient STT timeout, or fail Piper after real streamed audio. Controls expire after five minutes and do not change configured credentials. Default deployment leaves them disabled. Test doubles verify failure logic; only live-provider recordings/logs establish the real external-provider demonstration.

Production monitoring should alert on provider-specific timeout/auth/429 rates, queue age, recovery frequency, Redis errors and heartbeat failures. Add a deployment-wide circuit breaker with bounded probes and admission control; it is not implemented as an automatic secondary-provider switch here. During a chat-provider outage, preserve context, show unavailable/retry guidance, and permit existing human handoffs. Do not claim successful escalation if Redis persistence fails.

A secondary STT/model/TTS provider can change transcripts, language support, refusal behavior, tool schema adherence, voice and latency. Requalify it against the same held-out safety/tool/grounding suites, preserve turn IDs and authorization boundaries, and record provider changes. Never automatically weaken guards or convert return eligibility into refund initiation for availability. If transaction outcome is unknown, reconcile the persisted idempotency record before retrying; do not issue a second side effect.
